# 开发汇报约定

> 约定对象：开发者（我）↔ 项目负责人（你）
> 生效时间：从第一个开发模块开始，每次开发完一个模块都按本约定汇报。

---

## 1. 什么时候汇报

每完成一个**可独立验证的模块 / 功能闭环**就汇报一次，不等所有模块做完。
粒度按「**玩家能操作到什么程度**」划分——**不要**把"写了 5 个文件"当成一次汇报。

> 例：牌组 + 开局发牌 / 回合主循环 / 宽松叠牌 / +4 挑战 / 本地 AI 四档难度 / 智谱混合决策 / UI 对接引擎。

## 2. 每次汇报的固定四段式（**已被 §7 覆盖，仅作历史留存**）

> 2026-11-07 用户新指令：汇报输出改为**三段式**（开发了什么 / 能实现什么样的效果 / 还剩什么），见 §7。以下四段式不再作为对外输出格式。

````markdown
## 【模块编号 · 模块名】开发完成汇报

### 一、本次新增功能（操作层面）
- 用"玩家现在可以……"的句式写。
  - 例：玩家可以在轮到自己时点击高亮手牌打出；点击「摸牌」摸 1 张。
  - 例：抽到能出的牌时，界面会询问「立即打出 / 结束回合」。
- 只写用户能感知到的操作，不写"写了一个 reducer"这类实现细节。

### 二、可实现的效果
- 规则效果：这轮之后哪些规则真正生效了（例：+2 可以叠 +2/+4，累计摸牌）。
- 界面效果：玩家能看到什么（例：可出牌高亮、叠牌徽标显示累计张数）。
- 数据/日志效果：能查到什么（例：每步操作产生事件日志）。

### 三、还差哪些模块没开发（进度更新）
- 用表格给出状态：✅ 已完成 / 🚧 进行中 / ⏳ 等待外部 / ⬜ 未开始 / ⏸ 暂不做。
- **必须附「下一步计划」**：下一个要做的模块是什么、预计产出什么。
- 同时更新 `docs/开发进度.md` 的状态表（见第 4 节）。

### 四、怎么验证 + 已知限制
- 验证方式：命令 / 浏览器入口 / 测试结果（**只写实际跑过的，不夸大**）。
- 已知限制：这轮还不能做什么、哪些是占位、哪些等 UI 对接后才能操作。
- 需要你确认的点（如有）：规则歧义、手感偏好、默认值。
````

## 3. 撰写规则

1. **操作语言优先**：先回答"我现在能玩到什么、能做什么操作、会看到什么效果"，再谈技术。
2. **诚实标注**：没验证过的不要说"已实现"；引擎阶段（UI 还没对接时）要明确"当前只能通过命令行 / 测试验证，浏览器里还操作不了"。
3. **必须写"还差什么"**：每份汇报都要有未完成模块清单和下一步，不允许只报喜。
4. **附可复现的验证方式**：命令、URL、测试用例名，方便你自己复核。
5. **有歧义先问**：实现中遇到规则 / 手感取舍，汇报里单独列出"需要你确认"，不擅自定死。

## 4. 进度台账

每次汇报时同步更新 `docs/开发进度.md`：模块状态表（✅/🚧/⏳/⬜/⏸）、当前正在做的模块、最近一次汇报的模块编号与结论、未完成模块清单。

> 目的：即使隔了几天再回来，打开一个文件就能看到全貌。

## 5. 开发节奏规则（2026-10-17 补充，**优先级最高**）

**未经用户明确说「开始 Mx 模块的开发」，不要自行开始下一个模块。**（v2 阶段执行编号已定为 M1~M8；V2-00~V2-07 仅作验收对照。）

1. **一个模块做完立即停手**：完成当前模块的代码、自检、汇报后，进入「等待测试」状态——不继续写下一个模块，也不顺手做重构、优化、新功能。
2. **等用户测试**：汇报里必须给出清晰的测试步骤（打开哪个地址、点什么、预期看到什么），让用户能自己验证。
3. **等反馈，只修 bug**：用户测试后会给反馈；此阶段只做「修 bug / 按反馈调整」，不做新模块开发。
4. **修完继续等**：bug 修完后再次汇报"已修复 + 如何复验"，然后继续等待，直到用户说开始下一个模块。
5. **用户说「开始 Mx」后**才进入该模块开发；每次汇报的"当前状态"一栏要明确写：`等待你测试` / `修复完成待复验` / `等待你确认开始下一模块`。
6. 用户没有明确指令时**默认保持等待**，不要以"顺手做掉"为理由继续开发。

> 本条优先于本文件前面所有"开发顺序 / 并行建议"等内容。
>
> **补充说明（2026-10-19）**：**纯方案与文档类工作**（如策划新阶段、更新交接文档、压缩台账）不需要「开始 Mx」指令；但**只要涉及写实现代码，就必须等用户明确指令**。
>
> **2026-11-07 补充**：「未说开始不开工」「一个模块做完停手」仍然生效；但「汇报里给测试步骤 / 修完再次汇报复验方式」等**输出形式**改由 §7 三段式约束，自检仍必做、只是不单独成段。批准后的 commit / tag 流程见 §7。

## 6. UI 硬性规定：连续曲率圆角（2026-11-07 用户指令，**优先级最高**）

1. **一切 UI 圆角必须是连续曲率**（squircle / 超椭圆），**禁止** `border-radius: Npx` 的普通圆弧——直线与圆弧交界处曲率突变，不符合本项目的视觉基线。覆盖图标、卡片、面板、按钮、输入框、弹窗、牌面裁切等所有元素。
2. 统一资源 `apps/web/assets/squircle.svg`（超椭圆 `n=5`，归一化 `viewBox="0 0 1 1"`），全局 token `--ui-squircle`（`styles/tokens.css`）；标准 CSS 写法、滤镜与遮罩的顺序、验收口径见 [`UI优化方案-待开发.md`](./UI优化方案-待开发.md) §0。
3. 本条规定**即刻生效**：任何新增或改动的 UI 代码必须先套 squircle 遮罩；存量元素按 U4 逐步替换，不允许新代码继续引入普通圆角。
4. 同条已写入 [`开发进度.md`](./开发进度.md) §4 红线第 11 条，两处冲突时以本节为准。

## 7. 汇报、自检与提交流程硬性规定（2026-11-07 用户指令，**优先级最高**）

**一条规定，三款必须同时执行：**

1. **汇报只输出三段**。每次开发（含文档 / 配置 / 图标等修改）完成后，对外输出**只包含**：
   ① **开发了什么** → ② **能实现什么样的效果** → ③ **还剩什么**。
   不得出现第四段（验证方式、已知限制、待确认点、下一步计划明细等一律不单独成段，必要信息并入三段内）。
   本款覆盖 §2 四段式、§3 第 4 条「附可复现验证方式」与第 5 条「单独列出需要确认」的**输出形式**；
   歧义仍必须问，但并入「还剩什么」或用提问工具提出，不另开段落。
2. **改完文件必须自行验证无 bug 才能汇报**。按改动范围选择并实际跑过：
   `npm run lint` / `npm run typecheck` / `npm test` / `npm run verify:ui` / `verify:online`；
   文档改动校验内部链接与红线编号一致性；UI 改动用无头浏览器截图核对；打包改动核对哈希与产物内容。
   **验证结果不单独成段**，只在三段内用一句话带过；没跑过的不写，失败不得隐瞒。
3. **批准即提交，先 commit + tag，再开工**。用户批准「开始下一步开发」后，按此顺序自动执行：
   ① 对**上一阶段已完成成果** `git commit`（ Conventional 风格，如 `feat(ui): U1 右栏信息回归`）；
   ② 打该阶段 tag（U 系列用 `u1` / `u2` / `u3` / `u4`，v2.2 发布线沿用 `v2.2.0*`；同名已存在追加 `-2`）；
   ③ 确认 commit 与 tag 落盘后，**才开始下一步开发**。
   **不做 push**（当前授权仅含 commit 与 tag），不提交 `.env` / 日志 / 验收产物；纯文档与配置修改随下一次批准合并提交，不单独打 tag。

**首次批准的存量口径**：当前工作区有一批历史未提交改动（v2.2 N3/N4a/N4b、启动动画、大厅巨型牌、图标、总档压缩）。首次批准时先按逻辑分组补 commit（`feat(ui): v2.2.0 N3/N4a/N4b` / `feat(ui): 启动动画与大厅巨型牌` / `chore(icon): 透明连续曲率图标` / `docs: 开发总档与 U 系列计划`），再打基线 tag `u0-baseline`，然后才开工 U1。

**冲突优先级**：本节 > §2 / §3 / §5 输出与流程条款；§5「未说开始不开工、做完即停」、§6「连续曲率圆角」继续生效。同条已写入 [`开发进度.md`](./开发进度.md) §4 红线第 12 条与 [`开发总档.md`](./开发总档.md) §5 第 8 条。
