# 开发汇报约定

> 约定对象：开发者（我）↔ 项目负责人（你）
> 生效时间：从第一个开发模块开始，每次开发完一个模块都按本约定汇报。

---

## 1. 什么时候汇报

每完成一个**可独立验证的模块 / 功能闭环**就汇报一次，不等所有模块做完。
粒度按「**玩家能操作到什么程度**」划分——**不要**把"写了 5 个文件"当成一次汇报。

> 例：牌组 + 开局发牌 / 回合主循环 / 宽松叠牌 / +4 挑战 / 本地 AI 四档难度 / 智谱混合决策 / UI 对接引擎。

## 2. 每次汇报的固定四段式

````markdown
## 【模块编号 · 模块名】开发完成汇报

### 一、本次新增功能（操作层面）
- 用"玩家现在可以……"的句式写。
  - 例：玩家可以在轮到自己时点击高亮手牌打出；点击「摸牌」摸 1 张。
  - 例：抽到能出的牌时，界面会询问「立即打出 / 结束回合」。
- 只写用户能感知到的操作，不写"写了一个 reducer"这类实现细节。

### 二、可实现的效果
- 规则效果：这轮之后哪些规则真正生效了（例：+2 可以叠 +2/+4，累计摸牌）。
- 界面效果：玩家能看到什么（例：可出牌高亮、叠牌徽标显示累计张数）。
- 数据/日志效果：能查到什么（例：每步操作产生事件日志）。

### 三、还差哪些模块没开发（进度更新）
- 用表格给出状态：✅ 已完成 / 🚧 进行中 / ⏳ 等待外部 / ⬜ 未开始 / ⏸ 暂不做。
- **必须附「下一步计划」**：下一个要做的模块是什么、预计产出什么。
- 同时更新 `docs/开发进度.md` 的状态表（见第 4 节）。

### 四、怎么验证 + 已知限制
- 验证方式：命令 / 浏览器入口 / 测试结果（**只写实际跑过的，不夸大**）。
- 已知限制：这轮还不能做什么、哪些是占位、哪些等 UI 对接后才能操作。
- 需要你确认的点（如有）：规则歧义、手感偏好、默认值。
````

## 3. 撰写规则

1. **操作语言优先**：先回答"我现在能玩到什么、能做什么操作、会看到什么效果"，再谈技术。
2. **诚实标注**：没验证过的不要说"已实现"；引擎阶段（UI 还没对接时）要明确"当前只能通过命令行 / 测试验证，浏览器里还操作不了"。
3. **必须写"还差什么"**：每份汇报都要有未完成模块清单和下一步，不允许只报喜。
4. **附可复现的验证方式**：命令、URL、测试用例名，方便你自己复核。
5. **有歧义先问**：实现中遇到规则 / 手感取舍，汇报里单独列出"需要你确认"，不擅自定死。

## 4. 进度台账

每次汇报时同步更新 `docs/开发进度.md`：模块状态表（✅/🚧/⏳/⬜/⏸）、当前正在做的模块、最近一次汇报的模块编号与结论、未完成模块清单。

> 目的：即使隔了几天再回来，打开一个文件就能看到全貌。

## 5. 开发节奏规则（2026-10-17 补充，**优先级最高**）

**未经用户明确说「开始 Mx 模块的开发」，不要自行开始下一个模块。**（v2 阶段执行编号已定为 M1~M8；V2-00~V2-07 仅作验收对照。）

1. **一个模块做完立即停手**：完成当前模块的代码、自检、汇报后，进入「等待测试」状态——不继续写下一个模块，也不顺手做重构、优化、新功能。
2. **等用户测试**：汇报里必须给出清晰的测试步骤（打开哪个地址、点什么、预期看到什么），让用户能自己验证。
3. **等反馈，只修 bug**：用户测试后会给反馈；此阶段只做「修 bug / 按反馈调整」，不做新模块开发。
4. **修完继续等**：bug 修完后再次汇报"已修复 + 如何复验"，然后继续等待，直到用户说开始下一个模块。
5. **用户说「开始 Mx」后**才进入该模块开发；每次汇报的"当前状态"一栏要明确写：`等待你测试` / `修复完成待复验` / `等待你确认开始下一模块`。
6. 用户没有明确指令时**默认保持等待**，不要以"顺手做掉"为理由继续开发。

> 本条优先于本文件前面所有"开发顺序 / 并行建议"等内容。
>
> **补充说明（2026-10-19）**：**纯方案与文档类工作**（如策划新阶段、更新交接文档、压缩台账）不需要「开始 Mx」指令；但**只要涉及写实现代码，就必须等用户明确指令**。
